# RMC Backup Operations

This document describes the Docker backup system used by RMC.

## What the backup system does

The backup worker runs in the `crm_backup` Docker container. Each run:

1. Creates a PostgreSQL custom-format database dump.
2. Exports PostgreSQL tables as CSV files.
3. Creates a MongoDB archive when MongoDB backup is enabled.
4. Writes a manifest and compresses the run into a `.tar.gz` archive.
5. Sends the archive to the configured Telegram backup group.
6. Sends the exported, non-sensitive table data to Google Sheets through Google Apps Script.
7. Removes local backup folders older than `BACKUP_RETENTION_DAYS`.
8. Records the run as `started`, `success`, or `failed` in the PostgreSQL `backup_runs` table.

The complete database dump remains in the archive. Google Sheets is intended for readable operational data, not as the primary restore source.

## Schedule

The Docker worker runs every day at midnight in Uzbekistan time:

```env
BACKUP_TIMEZONE=Asia/Tashkent
BACKUP_HOUR=00
BACKUP_MINUTE=00
```

The schedule is implemented by `backup/entrypoint.sh`; host cron, `npm`, `dnf`, and `systemd` are not required.

The worker also checks the shared control volume every five seconds for a manual trigger.

## Manual backup button

Use:

**Engineering → Backup → Run backup now**

The button calls the owner-only endpoint:

```text
POST /api/system/backup
```

The backend writes a `run-now` trigger file to the shared `backup_control` Docker volume. The `crm_backup` container detects that file and starts a manual run. The button returns immediately; the final result appears in **Engineering → Backup** after the worker finishes.

Overlapping runs are prevented by a lock directory in the same control volume.

## Telegram delivery

Telegram receives the compressed backup archive only. The worker does not send separate success or failure status messages.

Create a Telegram group and:

1. Add the backup bot to the group.
2. Send a message in the group.
3. Read the group `chat.id` using the Telegram Bot API `getUpdates`.
4. Use the group ID in `service/.env`.

Group IDs commonly look like:

```env
BACKUP_TELEGRAM_CHAT_ID=-1004356466257
```

Required settings:

```env
BACKUP_TELEGRAM_BOT_TOKEN=...
BACKUP_TELEGRAM_CHAT_ID=-100...
BACKUP_TELEGRAM_CAPTION=RMC automated backup
```

The bot must be a member of the group and have permission to send documents. Backup Telegram credentials are separate from the student Telegram bot credentials.

## Google Sheets delivery

Google Sheets export uses the Apps Script web app configured by:

```env
GOOGLE_APPS_SCRIPT_URL=https://script.google.com/macros/s/YOUR_DEPLOYMENT_ID/exec
GOOGLE_SHEETS_TABLES=all
```

With `GOOGLE_SHEETS_TABLES=all`, the exporter discovers every PostgreSQL CSV generated by the current backup run. New database tables are included automatically after they are added to the schema and exported.

The exporter excludes only sensitive credential material from Sheets, including:

- `superusers`, `owners`, and `teacher_payment_credentials` tables
- Columns containing passwords, hashes, tokens, secrets, credentials, private keys, or API keys

The full unmodified PostgreSQL dump is still stored in the backup archive and is the source used for complete restoration.

The Apps Script must be deployed as a Web App with:

- **Execute as:** Me
- **Who has access:** Anyone
- URL ending in `/exec`

The script is stored in:

```text
scripts/google_apps_script.gs
```

## Environment configuration

`docker-compose.yml` loads:

1. `service/.env.example` as the baseline template.
2. `service/.env` as the optional local/server override.

The real `service/.env` is ignored by Git and must contain production secrets. Do not commit Telegram tokens, database passwords, JWT secrets, or other credentials.

Important backup settings:

```env
BACKUP_EXPORT_POSTGRES_TABLES=true
BACKUP_MONGO=true
BACKUP_RETENTION_DAYS=14
BACKUP_TIMEZONE=Asia/Tashkent
BACKUP_HOUR=00
BACKUP_MINUTE=00
GOOGLE_SHEETS_TABLES=all
```

## Deploy or update the worker

From the repository root on the server:

```bash
git pull
docker compose up -d --build backup
```

Check that the container is running:

```bash
docker compose ps backup
```

Verify the database backup tools:

```bash
docker exec crm_backup pg_dump --version
docker exec crm_backup mongodump --version
```

The PostgreSQL client should be version 16 or newer to match the PostgreSQL 16 server.

## Verify a manual run

1. Open **Engineering → Backup**.
2. Click **Run backup now**.
3. Wait for the run to change from `running` to `success` or `failed`.
4. Confirm the archive appears in the Telegram group.
5. Confirm the expected tabs appear or update in Google Sheets.

View worker output:

```bash
docker logs --tail 200 crm_backup
```

List stored backup runs:

```bash
docker exec crm_backup sh -c 'ls -lah /backups'
```

Inspect the latest run:

```bash
docker exec crm_backup sh -c '
latest=$(ls -1dt /backups/*/ 2>/dev/null | head -1)
echo "$latest"
cat "$latest/backup.log"
'
```

## Troubleshooting

### PostgreSQL server version mismatch

Error:

```text
pg_dump: error: aborting because of server version mismatch
```

Rebuild the backup image so it uses the PostgreSQL 16 client:

```bash
docker compose build --no-cache backup
docker compose up -d backup
```

### Telegram archive is not delivered

Check the worker log and the saved Telegram response:

```bash
docker logs --tail 200 crm_backup
docker exec crm_backup sh -c '
latest=$(ls -1dt /backups/*/ 2>/dev/null | head -1)
cat "$latest"/telegram_response_*.json
'
```

Common causes:

- The bot token is invalid or revoked.
- The bot is not a member of the group.
- The group ID is a personal user ID instead of the group ID.
- The bot cannot send documents in the group.
- The archive exceeds the Telegram upload limit and a part upload fails.

### Google Sheets is not updated

Check that the worker received the Apps Script settings:

```bash
docker exec crm_backup sh -c '
for key in GOOGLE_APPS_SCRIPT_URL GOOGLE_SHEETS_TABLES BACKUP_EXPORT_POSTGRES_TABLES; do
  if printenv "$key" | grep -q .; then echo "$key=SET"; else echo "$key=MISSING"; fi
done
'
```

Then inspect the export log in the latest run:

```bash
docker exec crm_backup sh -c '
latest=$(ls -1dt /backups/*/ 2>/dev/null | head -1)
cat "$latest/sheets_export.log"
'
```

Confirm that the Apps Script URL ends in `/exec` and that the Web App access setting allows the backup worker to call it.

### Backup page shows failed

The **Engineering → Backup** page reads from `backup_runs`. The error column contains the latest recorded failure detail. The complete worker log is stored in the run directory as `backup.log`.

A run can fail after the database dump—for example during Telegram upload or Sheets export—so always inspect the worker log to identify the exact stage.

## Restore note

The Telegram archive and persistent `backup_data` volume contain the backup artifacts. A PostgreSQL custom-format dump can be restored with PostgreSQL `pg_restore`, and the MongoDB archive can be restored with `mongorestore`.

Before restoring production data, stop application writes and verify the target database and credentials. Do not restore directly over production without a tested recovery procedure.
