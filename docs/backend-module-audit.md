# RMC Backend Module Audit

**Scope:** `service/` (the live Express + TypeScript + PostgreSQL backend — confirmed active via root `package.json`'s `dev`/`start` scripts). The `nest/` directory is an unfinished, unmounted NestJS port of the same app and was excluded. `service/src/modules/drizzle_repositories/` contains only a test file (no controller/service/repository) and was excluded as not a real business module.

**Method:** 5 parallel agents each reviewed a group of modules (controllers, services, repositories, routes, DTOs, and `db/schema.ts`) for: DTO validation coverage, service-layer edge-case handling, repository consistency (including SQL-injection risk), entity/schema ownership, and concrete bugs.

---

## Critical / High-severity findings (read this first)

1. **Privilege escalation — `superusers` module.** `superuserRoutes.ts` has no per-route role check beyond the mount-level `requireRole('superuser')`. Any center-admin-level superuser can `POST`/`PUT /api/superusers` with `role: 'owner'` to mint a new owner account or self-promote, and can `DELETE` other superusers/owners. No DTO restricts the `role`/`permissions` fields. — `modules/superusers/controllers/superuser.controller.ts:28-56`, `services/superuser.service.ts:54,73`.
2. **Cross-tenant IDOR — `rooms` module.** `rooms.controller.ts`, `room-slots.controller.ts`, and `room-insights.controller.ts` resolve `centerId` as `req.query.center_id || req.body?.center_id || req.user.center_id` — client-supplied value wins, with no check that the caller is an owner/global user (unlike every other module, which uses `shared/tenant.ts`'s `getScopedCenterId`). Any teacher or non-owner superuser can read/write another center's rooms, slots, bookings, and physical rooms by passing a different `center_id`. Additionally, `GET /api/room-slots/bookings/slot/:slotId` is unscoped by center entirely, no spoofing needed.
3. **Unauthenticated financial/PII data exposure — `telegram_students` module.** All routes under `/api/telegram/student/*` (`menu`, `last-lesson`, `rankings`, `results`, **`payments`**) are mounted with no `requireAuth` and no bot-token/HMAC verification — only a client-supplied `telegram_user_id`. Anyone who knows/guesses a student's Telegram user ID can read their grades, coin balance, and payment history. Needs explicit confirmation of whether this is an intentional "trust the bot's network boundary" design or a gap.
4. **Owner self-registration uses a hardcoded fallback secret.** `owner.controller.ts:66` — `OWNER_INVITE_KEY` defaults to the literal string `'owner-create-2026'` if the env var isn't set in production. The registration endpoint is mounted unauthenticated. Also, account lockout (`is_locked`) is never actually set despite `login_attempts` being tracked (same gap in `superusers`).
5. **Financial edge-case gaps.** `debts` create/update has **no DTO validation at all** — negative `debt_amount`/`amount_paid` and over-payment (producing negative balances) are accepted. `refunds.dto.ts`'s `amount` field is missing `@Min(0)` (every other money DTO has it), and nothing checks a refund amount against the original payment or prior refunds — a refund can exceed the payment it's against.
6. **Zero DTO validation on entire modules:** `subjects`, `assignments`, `rooms`/`room-slots`, `centers`, `superusers`, `translations`, `system`, `settings`, `audit_logs`, `archive` have no DTO classes at all for their mutating routes (validation, where present, is manual/ad hoc). `assignments` additionally has a dead, **unauthenticated duplicate router** (`modules/assignments/routes/assignment.routes.ts`) that isn't mounted but still exists in the codebase — should be deleted to avoid future confusion.
7. **Dead/misleading columns and logic:**
   - `audit_logs.center_id` column is never populated — every write stuffs `center_id` into the `details` JSONB blob instead, so center-scoped audit queries do an unindexed JSONB text scan.
   - `debts` table has unused legacy `amount`/`paid_amount` columns (real ones are `debt_amount`/`amount_paid`).
   - `parents.center_id` is never populated by the insert path — always NULL.
   - `teachers`' `force`-delete flag is validated and read by the controller but never consumed by the service — dependencies are always silently auto-unassigned; the controller's "blocked"/"has_dependencies" responses are dead code.
   - `db/schema.ts` defines a `class_sessions` table that duplicates `sessions` and is never referenced by any repository/service.

No raw string-concatenated/interpolated SQL (classic SQL-injection risk) was found in any of the 37 modules — all repositories use Drizzle's query builder or parameterized `sql` tagged templates.

## Cross-cutting observations
- **Validation pattern is inconsistent across the codebase**: most modules use `class-validator` DTOs wired via `validateBody/validateParams/validateQuery` middleware, but `owners` uses zod validated inline, and roughly a third of modules (`subjects`, `assignments`, `centers`, `superusers`, `translations`, `system`, `settings`, `audit_logs`, `archive`, `rooms`) have no DTO layer at all, relying on ad hoc manual checks of varying rigor.
- **Tenant scoping pattern is inconsistent**: `shared/tenant.ts`'s `getScopedCenterId` (used by students/teachers/most modules) correctly restricts center-override to global/owner users. `rooms` and, to an extent, `system`/`settings`/`audit_logs`/`archive`/`import_export` reimplement scope-checking ad hoc instead of using the shared helper — `rooms` gets it wrong (see Critical Finding #2); `reports` uses a newer, cleaner shared-helper pattern that other modules should be migrated toward.
- **Transactional consistency around money is uneven**: `salaries`/`kpis` use correct upserts; `payments`, `payment_plans`, `invoices`, `debts`, `refunds` all have at least one non-atomic multi-write sequence that could leave partial/inconsistent state on failure.
- **No SQL-injection risk found** anywhere — all data access goes through Drizzle's query builder or parameterized `sql` tagged templates; the few `sql.raw` usages found are all guarded by hardcoded allowlists, not raw user input.

## A.2 Items the audit did not cover

These sit outside the module-by-module scope but outrank several listed findings.

- **Passwords are unsalted SHA-256.** `shared/password.ts` is a bare `crypto.createHash('sha256')` digest, applied to owners, superusers, teachers, and students alike. `bcryptjs` is already a declared dependency in `service/package.json` and is never imported. This compounds Critical Finding 4's unimplemented lockout.
- **No rate limiting and no security headers.** `express-rate-limit` and `helmet` are both declared dependencies and neither is wired into `service/src/index.ts`. Login endpoints are unthrottled.
- **CORS is fully open.** `app.use(cors())` is called with no origin allowlist.
- **`shared/tenant.ts` has its own header-spoofing path.** For non-global users, `getScopedCenterId` falls back to `req.headers` when `req.user` carries no center value. Teacher tokens do include `center_id`, so this only opens where a row has a NULL center, but the "correct" helper is not unconditionally safe.
- **The invite-key fallback is also the documented default.** `service/.env.example` ships `OWNER_INVITE_KEY=owner-create-2026`, the same literal as the hardcoded fallback, and the UI carries the identical fallback in `OwnerRegisterPage.tsx`. Operators are likely to deploy that exact value.
- **Index declarations live only in migrations.** `db/schema.ts` declares no indexes while the migrations create 132. Anyone reading the schema file as the source of truth on performance will draw the wrong conclusion. This is drift, not a missing index.

## A.3 Efficiency summary

Runtime performance is better than the finding list implies. The database is properly indexed, all data access is parameterized, and `tsc` is clean. The N+1 and in-memory-aggregation hot spots sit in reports, imports, debt analysis, and bulk writes rather than on hot read paths.

Await-in-loop sites were found in `debts`, `grades`, `import_export`, `invoices`, `payment_plans`, `rooms`, `salaries`, `sessions`, `students`, `teachers`, `tests`, and `translations`.

The three worst pure-performance items, in order:

1. `audit_logs` center filtering by unindexed JSONB text extraction, on the fastest-growing table, with unbounded limit and offset.
2. `import_export` doing one database round trip per imported row with no batching and an untimed external fetch.
3. `translations` bulk upsert holding a single transaction open across an uncapped array of sequential per-row writes.

Expected gain from implementing the audit in full: a large security and data-integrity improvement, and a small speed improvement confined to reports, imports, and debt analysis. Elsewhere the change is not measurable.

# Appendix B — UI impact of the remediations

**Governing constraint: the current UI behaviour is user-approved and must not change.** Each remediation below is therefore assessed for whether it alters what a user sees or can do. Where it would, the note states the implementation constraint that keeps present behaviour intact, rather than proposing a new behaviour.

## B.1 The silent-strip risk, which applies to every new DTO

`service/src/middleware/validation.ts` runs `class-validator` with `whitelist: true` and `forbidNonWhitelisted: false`. Fields not declared on the DTO are **silently removed** from the request body. The client receives 200 and no error.

Adding a DTO to any currently-unvalidated module therefore risks silently dropping fields the UI already sends. The failure is invisible in the network tab and in the UI.

This matters most where the UI submits a whole fetched row rather than a hand-built payload. `useDebtsPage.ts` does exactly that: `handleOpenModal` calls `setFormData(debt)` with the full record, and `handleSubmit` posts `formData` unchanged. Every column the API returned, including joined display fields, goes back up.

**Constraint:** build each new DTO from the payload the UI actually sends, verified against the relevant `api.ts` and form hook, not from the database schema. Any field the UI sends today and the DTO omits stops persisting, with no error, which is a behaviour change.

## B.2 Backend changes that need no UI change

| Remediation | Why the UI is unaffected |
|---|---|
| Rooms tenant scoping via `getScopedCenterId` | The UI already sends `center_id` taken from `user?.center_id`, which is the same value the JWT carries, so scoped resolution returns an identical result for admins and teachers. Owners keep the query override that `getScopedCenterId` grants global users. |
| `telegram_students` authentication or removal | No consumer exists. The bot uses `pg.Pool` directly and calls only `api.telegram.org`. The UI never references `/api/telegram/student/*`. |

## B.3 Backend changes that require a matching UI change

Four, in priority order.

**1. Sidebar order role gate — do not apply as written.** The audit proposes adding `requireRole('superuser')` to the `sidebar-order` routes. `src/components/layout/Sidebar.tsx` calls `getSidebarOrder()` for every authenticated user regardless of role, and `saveSidebarOrder()` on reorder. A blanket role gate makes both 403 for teachers and students. The GET has a `.catch()` that falls back to an empty order, so the app will not crash, but every non-superuser silently loses their saved sidebar order. That is a user-visible behaviour change to an approved feature. Sidebar order is per-user data, not administrative configuration. Scope it by `req.user.id` instead of by role. No UI change is then needed.

**2. Superuser role restriction.** `src/features/owner/constants.ts:94` defines `role` as a required free-text field, and `useOwnerManager.ts:461` sends `role: String(formData.role || 'admin').toLowerCase()` on every submit. Once the backend restricts role assignment to owners, an admin's submit either 403s or has the field stripped, depending on implementation. The form must hide or disable the role field for non-owner callers so an admin never submits a value that will be rejected or silently dropped. Restricting the field is the intended effect of the fix, so this is the one place where an admin's capability legitimately narrows. Nothing changes for owners.

**3. Hard-delete permission flag.** `requireMuzaffarHardDelete` in `middleware/auth.ts:147` checks `username === 'muzaffar'`. The UI mirrors that literal in three places: `useOwnerManager.ts:148`, `useOwnerManager.ts:564`, and `ArchivePage.tsx:79`. Moving to a permission flag requires updating all three to read the flag. To preserve behaviour exactly, seed the flag on that account as part of the migration so the same person retains the same capability and no one else gains it.

**4. Owner invite key.** `OwnerRegisterPage.tsx:27` carries the same hardcoded fallback as the backend. Removing the backend fallback without removing the UI fallback produces a registration form that accepts the key locally and then fails server-side. Both fallbacks must be removed together, and `VITE_OWNER_INVITE_KEY` must be set wherever registration is enabled.

# Appendix C — Backend test-coverage correction

Everything above this line, including Appendix A and B, was written and validated against the assumption that `service/` had zero automated tests. It does not change any of the correctness findings in the Critical Findings section or the master table — those were verified by reading the actual code paths, not by checking test coverage — but it does change the coverage picture throughout the document.

**What was actually missed:** the original research searched only for `*.test.ts` and `*.spec.ts` files and found none, plus two empty directories (`service/test/e2e`, `service/test/integration`), and concluded the backend was untested. The backend's real convention is `.test.js` files living beside the code they test, at `modules/*/services/tests/*.test.js` (and a handful of controller/shared/middleware equivalents). Running `npx jest --runInBand --listTests` from `service/` finds 51 of them.

**Corrected coverage:** 34 of the 37 business modules have at least one backend test file. The three that do not: `teacherTasks`, `salaries`, and `tests` (the exam engine). Every "Backend: none. UI: ..." cell in the master table's Test coverage column is wrong except for these three modules' rows — treat "Backend: none" as "Backend: 1+ existing jest test file(s)" everywhere else in that column.

**What is still true:** the backend genuinely has zero *new* test files written specifically for the gaps this audit found (that was never claimed to exist independently of this miscount — the master table's "Tests needed & why" column describes tests that don't exist yet, which remains accurate). The UI's 45 unit specs and 34 e2e specs are also accurately counted; only the backend side of the coverage comparison in Appendix A.1 and B.5 was wrong.

**Practical effect on the QA ticket sheet:** the ticket originally scoped as "stand up the backend test harness, because none exists" is moot — a harness exists, is configured (`jest.config.cjs`, `jest.integration.config.cjs`), and already runs 51 test files.
