TEMURBEK SCHOOL LC Student and Parent Mobile App

Product Requirements Document · based on client brief TZ v2.0 (30.10.2026) and an audit of the RMC codebase · prepared 2026-10-30

1. Summary

The brief describes a 10-module learning platform. Built in full it is roughly 1,700 focused hours of work (see the timeline), about four years at 2 hours a day for one person. This PRD therefore keeps the client's full vision but splits it into releases, and puts three decisions first:

  1. RMC stays the source of truth. The mobile app is a new client of the existing service/ backend (Express + Postgres + Drizzle), exposed through a versioned /api/mobile/v1 namespace. The unfinished nest/ port is not extended.
  2. The first release is a trust-builder, not the whole LMS. Parents see attendance, grades, coins and payments; students see schedule and homework; everyone gets push notifications. This is mostly exposing data RMC already holds, so it is the cheapest and most visible win.
  3. Buy or reuse for the expensive parts. Live classroom, video hosting, chat and speech-to-text are built from managed services, not from scratch. The Telegram bot is kept as an adoption bridge for parents.
Two blockers to settle in Phase 0: (a) personal-data storage rules in Uzbekistan versus the current AWS hosting region; (b) Apple and Google billing rules for AI Premium and Premium Video. Both can change cost and architecture.

3. Goals and non-goals

Goals

  1. Parents see attendance, grades, coins, payments and teacher feedback in real time.
  2. Homework, mock exams and the monthly speaking assessment run inside one tracked flow.
  3. Students are rewarded for activity: coins, streaks, leaderboard, AI practice.
  4. The Owner can measure quality: surveys, teacher ratings, app adoption.

Non-goals

  • Replacing the CRM or rebuilding finance, salary and cash reporting inside the app.
  • Student-to-student private video calls (excluded by the brief).
  • Presenting AI scores as official IELTS or CEFR results.
  • Gating core lessons behind social-media follows.

6. Key improvements to the brief

6.1 Parents first

The brief ranks the student experience first, but RMC already has most student data and none of the parent API. Parents decide whether the school feels transparent and they pay the fees. Ship the parent portal and push notifications in the first release.

6.2 Use Telegram as the bridge

Many parents already use the bot. Add a deep link from bot messages to the app and keep Telegram as a fallback channel for notifications until app adoption passes the target.

6.3 One generic task engine

Six homework types and seven vocabulary mechanics sound like thirteen features. A JSON-schema driven task renderer makes them one feature plus content. Teachers and the Academic Director get faster authoring too.

6.4 Offline and weak-network behaviour

Cache dashboard, schedule and last grades; queue homework answers and exam autosaves locally and sync with idempotency keys. This also covers the "internet dropped during exam" requirement.

6.5 Social onboarding, honestly

  • Telegram: the bot can check membership with getChatMember if it is an admin of the channel, as the existing required-channel check does.
  • Instagram: no public API to verify a follow. Treat it as "open the page", with no verified state.
  • Show an accurate label ("Opened" / "Verified") instead of a checkbox that implies verification.

6.6 Store billing

  • Tuition is payment for a real-world service: external gateways (Payme, Click, Uzum) are normally allowed. Confirm current store policy before launch.
  • AI Premium and Premium Video are digital goods: expect Apple IAP and Google Play Billing with the store commission. Price accordingly or sell through the center (offline/CRM) and unlock by account.

6.7 Survey privacy that holds up

Store the respondent mapping separately from answers, show results only when a group has at least 5 responses, and report teacher ratings as aggregates. Decide the KPI weight and minimum respondent count with the Owner in writing.

6.8 Avoid building video infrastructure

  • Video lessons: managed HLS host with signed URLs.
  • Speaking videos: presigned upload straight to object storage, then transcode.
  • Live classroom: LiveKit, Agora or a Zoom SDK; whiteboard via an embeddable library.

6.9 Client technology

The brief recommends Flutter. The existing team code is TypeScript (React, Redux, Express). Recommendation: React Native with Expo if one developer owns both backend and app, because DTO types and API clients can be shared and push, OTA fixes and store builds are streamlined. Flutter is a fine choice if the developer prefers Dart or the client requires it. The prototype and API design are independent of this choice.

8. CRM integration

Since the "CRM" is RMC itself, integration means shared tables and internal events, not an external API. Ownership per entity:

DataOwner systemMobile access
Students, parents, parent links, groups, teachers, timetableRMCRead
Attendance, lesson grades, coin awards, payments, debtsRMCRead
Homework bank, submissions, exam attempts, speaking videos and scoresNew mobile tables in same PostgresRead and write; teacher-approved results copied to RMC grades
Coin spending, referralsSame ledger (student_coin_transactions)Server-side only
Surveys, news, links, policies, chat, AI usageNew mobile tablesRead and write by role

Events from RMC to app: lesson marked → open homework; attendance saved → push to parent; grade or coin posted → push; payment confirmed → push and referral check; debt created → reminder. Implement as an internal event bus and an outbox table, with idempotency keys so retries do not duplicate.

11. Security and compliance

  • Auth: short-lived access token (15 min), rotating refresh token, device list with remote sign-out, password reset, rate limits, optional biometric unlock.
  • Parent link: only through an RMC-approved parent_students row; the app can request a link but cannot create one.
  • Data isolation: every query is scoped by center_id and by the caller's role; add automated tests for cross-student and cross-parent access.
  • Minors: consent for video recording, retention rules (propose 12 months for speaking videos), no public student profiles, chat moderation with reporting and blocking.
  • Encryption: TLS everywhere, encrypted storage and backups, secrets out of the compose file.
  • Data residency: Uzbekistan's personal-data law requires attention to where citizens' data is stored. Production runs on AWS EC2; confirm region and whether a local server or provider is required. Get legal confirmation in Phase 0.
  • Store policies: privacy labels, account deletion in-app, children's data declarations, content rating.
  • Audit: extend audit_logs to mobile writes, moderation actions and policy acceptances.
